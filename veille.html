Utilisation d'Ansible avec Linux et Windows

Sujet

Ma veille porte sur l'utilisation d'Ansible pour automatiser l'administration de machines Linux et Windows dans un parc informatique.

Problématique : comment l’évolution d’Ansible pourrait-elle transformer l’administration des systèmes Linux et Windows et quels seront ses impacts sur la sécurité, l’organisation et les métiers en entreprise ?

Stratégie de veille

Objectif SISR : suivre les possibilités et les limites de l’automatisation d’un parc Linux et Windows, en privilégiant des informations vérifiables.

  • Sources prioritaires : documentation officielle Ansible pour les prérequis, la sécurité et les évolutions de support ; forum officiel pour les annonces à recouper avec la documentation.
  • Outils : navigateur et journal de lecture conservé sur cette page. Aucun agrégateur RSS ni alerte n’est déclaré comme déjà configuré.
  • Fréquence prévue : une recherche quotidienne sur les nouveautés, complétée par une synthèse régulière de leur impact en entreprise. Les recherches sont datées et seules les évolutions pertinentes sont ajoutées au journal ; une journée sans nouveauté ne justifie pas une entrée artificielle.
  • Méthode : relever la source, sa date de consultation, le changement ou point technique, puis son impact pour mon environnement. Vérifier en laboratoire avant de proposer une utilisation en production.

Perspectives et impacts en entreprise

La veille ne se limite pas à apprendre à utiliser Ansible : elle suit son évolution vers une automatisation davantage intégrée aux événements, aux outils de supervision et aux assistants d’intelligence artificielle. Ces perspectives doivent être distinguées des capacités déjà disponibles et des fonctions encore en préversion.

  • Organisation : des tâches standardisées et des portails en libre-service pourraient réduire certaines interventions manuelles. L’équipe doit définir les opérations autorisées et leurs validations.
  • Métier SISR : l’administrateur pourrait consacrer davantage de temps à concevoir, tester et contrôler les automatisations plutôt qu’à répéter des installations.
  • Sécurité : multiplier les actions automatiques augmente l’importance des habilitations, des secrets temporaires et de la traçabilité. Une erreur peut aussi se propager plus vite.
  • Coûts : les gains possibles doivent être comparés au temps de formation, de maintenance des playbooks et au coût des outils. Aucun gain chiffré n’est affirmé sans mesure.

Il s’agit de mon analyse prospective, pas de résultats mesurés chez AESysteme. Les fonctions de la plateforme commerciale Red Hat Ansible Automation Platform ne sont pas automatiquement incluses dans ansible-core.

Qu'est-ce qu'Ansible ?

Ansible est un outil open source d'automatisation informatique. Il permet d'installer des logiciels, configurer des serveurs, deployer des applications et executer des taches d'administration sur plusieurs machines.

Il fonctionne avec des fichiers appeles playbooks, ecrits en YAML. Ces playbooks decrivent les actions a effectuer. Ansible applique ensuite ces actions sur les machines indiquees dans un inventaire.

Fonctionnement general

  • Une machine de controle lance les commandes Ansible.
  • Un inventaire liste les serveurs Linux et Windows a administrer.
  • Les playbooks decrivent les actions a realiser.
  • Les modules Ansible executent les actions : installation, copie de fichiers, services, utilisateurs, mises a jour.
  • Ansible est agentless : il n'est pas necessaire d'installer un agent permanent sur chaque machine.

Utilisation avec Linux

Sur Linux, Ansible utilise principalement SSH. C'est simple car SSH est deja present sur la plupart des serveurs Linux.

  • Connexion avec une cle SSH ou un mot de passe.
  • Utilisation de become pour executer certaines taches avec les droits administrateur.
  • Modules courants : apt, dnf, service, copy, template, user.
  • Cas d'usage : installer Apache, configurer un firewall, creer un utilisateur, deployer un fichier de configuration.

Utilisation avec Windows

Sur Windows, Ansible utilise surtout WinRM, un protocole de gestion a distance integre a Windows. Ansible peut aussi utiliser OpenSSH avec Windows, mais il faut respecter les versions supportees.

  • Connexion WinRM en HTTP ou HTTPS, avec une configuration prealable de la machine Windows.
  • Modules Windows : win_updates, win_service, win_user, win_copy, win_package.
  • Cas d'usage : installer un logiciel, gerer un service Windows, creer un utilisateur, appliquer des mises a jour.
  • Bonne pratique : privilegier WinRM en HTTPS ou une authentification adaptee au domaine.

Exemple d'inventaire

[linux]
srv-web ansible_host=192.168.1.10 ansible_user=admin

[windows]
pc-support ansible_host=192.168.1.20

[windows:vars]
ansible_connection=winrm
ansible_user=Administrateur
; Secret fourni séparément par une variable chiffrée avec Vault
ansible_winrm_transport=ntlm
ansible_port=5986
ansible_winrm_scheme=https
ansible_winrm_server_cert_validation=validate

Exemple de playbook

Exemple pédagogique non exécuté dans cette veille. Il suppose des hôtes accessibles, les droits adaptés et la collection ansible.windows installée. Il ne constitue pas une preuve de déploiement réalisé.

---
- name: Installer Apache sur Linux
  hosts: linux
  become: true
  tasks:
    - name: Installer apache2
      ansible.builtin.apt:
        name: apache2
        state: present

- name: Verifier un service Windows
  hosts: windows
  tasks:
    - name: Demarrer le service Spooler
      ansible.windows.win_service:
        name: Spooler
        state: started

Interet pour une entreprise

  • Gagner du temps sur les taches repetitives.
  • Limiter les erreurs humaines pendant les installations et configurations.
  • Gerer Linux et Windows dans un meme outil.
  • Documenter les actions grace aux playbooks.
  • Rejouer une configuration identique sur plusieurs machines.

Points de vigilance

  • Ne jamais stocker les mots de passe en clair : utiliser Ansible Vault.
  • Tester les playbooks sur un environnement de test avant la production.
  • Verifier les droits administrateur sur Linux et Windows.
  • Bien separer les groupes Linux et Windows dans l'inventaire.
  • Sur Windows, verifier la configuration WinRM, le firewall et le mode d'authentification.

Journal de veille — vérification du 22/11/2026

Les pages suivantes sont des documentations évolutives, sans date de publication unique affichée. La date indiquée est celle de consultation, et non une date de publication. Cette entrée ne prétend pas reconstituer des lectures antérieures.

  • Support Windows SSH : le support officiel a été ajouté à ansible-core 2.18. La documentation précise les prérequis OpenSSH et recommande PowerShell. Impact : vérifier les versions avant de choisir SSH plutôt que WinRM. Ansible — Windows SSH, consulté le 22/11/2026.
  • WinRM : nécessite un listener, une authentification adaptée et des dépendances Python côté contrôle. Impact : préparer la connectivité et valider le certificat HTTPS avant l’exécution. Ansible — Windows Remote Management, consulté le 22/11/2026.
  • Validation : le mode check simule les changements pour les modules compatibles ; le mode diff compare les modifications. Ces modes ne remplacent pas un test fonctionnel et certaines tâches peuvent être forcées à s’exécuter. Ansible — Check et diff, consulté le 22/11/2026.
  • Protection des secrets : Vault chiffre des variables ou fichiers sensibles. Impact : ne pas publier de mots de passe en clair avec les playbooks. Ansible — Vault, consulté le 22/11/2026.

Synthèse et analyse personnelle

Les acteurs principaux de cette veille sont la communauté Ansible, Red Hat et Microsoft pour les composants Windows. L’évolution du support officiel de SSH sur Windows élargit les choix de connexion ; elle ne supprime pas les contraintes propres à chaque système.

Le point essentiel pour mon parcours SISR est la reproductibilité : un playbook peut rejouer une configuration sur plusieurs serveurs, au lieu de répéter chaque action manuellement. Un serveur doit toutefois déjà être accessible, ou être provisionné par un mécanisme prévu dans l’automatisation. Ansible ne remplace pas à lui seul l’installation physique d’une machine.

Pour mes missions Ubuntu/Odoo, je pourrais étudier l’automatisation de la préparation du système et des services. Il s’agit d’une piste d’amélioration, pas d’un déploiement Ansible déjà réalisé. Je commencerais par deux machines de test, puis vérifierais une seconde exécution pour repérer les changements inutiles : l’idempotence dépend des modules et de la manière d’écrire les tâches.

Les enjeux sont le gain de temps, la cohérence des configurations, les droits d’administration et le risque de propager une erreur à plusieurs hôtes. Mon choix serait de tester sur un petit périmètre, protéger les secrets et garder une procédure de retour arrière.

Conclusion

Ansible est interessant pour administrer un parc mixte Linux et Windows. Linux est gere facilement avec SSH, tandis que Windows demande une configuration WinRM ou SSH plus precise. Pour une entreprise, Ansible permet de standardiser les configurations, gagner du temps et fiabiliser les deploiements.
